## 四、结构性风险

1. **设计器内部循环依赖 9 处**（5 文件环为主）：
   `Designer/Core/__init__.py → Core/ui/__init__.py → design_window_entry.py → {elements,element_factory,template_store,project_store,design_page,offline_run_dialog}.py → myQuadTreeScene.py → Core/__init__.py`。
   这类环由包级 `__init__` 的再导出造成，会放大导入顺序问题、也让“谁依赖谁”无法静态判定。
2. **App_SafetyCar 3 文件循环**：`__init__ → safety_car_entry → ip_setup → __init__`。
3. **Modbus 3 文件循环**：`__init__ → modbus_data_broker → modbus_plc_manager → __init__`。
4. **新旧场景并存**：Core 与 CoreQGraphics 同时被应用层依赖（RackConfig 49/38、SafetyCar 22/22），迁移未收敛，改动需要双份验证。
5. **工具脚本反向耦合产品代码**：tools 直接 import 各 App 的窗口类（如 `profile_pop_pick_perf.py` → `PopPickWindow`），属于 INFERRED 的“意外连接”，产品接口一变脚本就碎。

## 五、怎么用这张图

```bash
# 查某个主题（BFS，默认 2000 token 预算）
.venv/Scripts/graphify.exe query "吸附点是怎么算的"

# 追踪具体路径（DFS）
.venv/Scripts/graphify.exe query "sceneRect 怎么恢复" --dfs

# 两点之间最短路径
.venv/Scripts/graphify.exe path "base_element" "QuadTreeScene"

# 改 X 会波及谁（反向遍历）
.venv/Scripts/graphify.exe affected "BaseItem" --depth 2

# 架构枢纽排行
.venv/Scripts/graphify.exe god-nodes --top 20
```

代码改动后增量更新（无需 API）：`.venv/Scripts/graphify.exe update .`
