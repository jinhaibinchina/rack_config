## 修复 flip_clock PLC 时间解析崩溃
- 报错：get_time_parts_by_plc 中 `hours, minutes, seconds = now.split(":")` → ValueError/IndexError
- 根因：PLC 时间字符串非 HH:MM:SS（空串、段数不足、非两位数字、越界），且 get_string 在 PLC 字符串长度非法时会抛 TypeError
- 修复：新增 FlipDigit_Time_Display.parse_plc_time 严格校验（去空字节/空白、必须3段、每段2位数字、时<=23 分秒<=59），非法返回 None
- update_time_by_plc 遇到非法值保持当前显示并返回 False
- plc_window.handle_data_broker 中 get_string(datas,16) 包 try/except (TypeError, IndexError, UnicodeDecodeError) → None

## PLC 断线重连加固（plc_manager.py / data_broker.py / plc_window.py）
现场日志：Connection reset by peer → Unreachable peer → watchdog 超时 → 反复"尝试重连..."
根因与修复：
1. 死锁：connect/disconnect 在 self.lock 内做 TCP（可耗时数秒），UI 与轮询线程全部卡住
   → 锁只保护状态机，网络调用一律在锁外；_close_client/_open_client 自行加锁
2. 重连无退避：原 while not connected 里固定 5s，PLC 未上电时刷屏
   → 指数退避 2s→4s→8s，上限 15s（RECONNECT_MIN_DELAY/MAX_DELAY/BACKOFF）
3. 旧 client 不销毁：失败后 socket 残留
   → 每次连接前 _close_client()（disconnect + destroy）
4. IO 超时过长：默认无上限，db_read 可能卡很久
   → set_param SendTimeout/RecvTimeout=2000ms, PingTimeout=1000ms
5. 重连线程被心跳条件误杀：`while heartbeat_active` 在首次连接失败时立即退出
   → 改用 _stop_reconnect 标志
6. 轮询空转：断线时仍对 5 个 DB 逐个等超时
   → PollingThread 断线时直接 msleep(500) 跳过
7. plc_window 多处 read_data 返回 None 未判空（启动即 TypeError）
   → 全部补 None 判断 + get_string 包 try/except
新增 PLCManager.add_state_listener(cb) 供 UI 订阅"重连中/已连接/已断开"

## 修复关闭时 "QThread: Destroyed while thread is still running"
四层原因，全在关闭路径上：
1. tabbed_wigdet.closeEvent 引用已注释掉的 self._name / TabbedPlcWidget._instances
   → closeEvent 直接抛 AttributeError，后面的线程清理代码根本执行不到（这是主因）
2. closeEvent 原本没有任何线程清理逻辑 → 新增 _stop_all_tabs()
3. on_tabWidget_tabCloseRequested 用 currentTab() 而非 tab_widget.widget(index)
   → 关非当前标签时停错线程；改用 index，并 _existed_ips.discard 防 KeyError
4. main.MainWidget.closeEvent 只 event.accept() → 新增停 _timer + tabbed._stop_all_tabs()
配套：
- DataBroker 增加 parent 参数、start_data_polling 幂等、stop_data_polling(wait_ms=5000) 有上限、
  新增 shutdown()；去掉了对无事件循环线程无意义的 quit()
- WindowContainer 新增 shutdown() + closeEvent；_close_tab 优先调用 widget.shutdown()
验证：3 个标签页 → 关非当前页只停对应线程 → 关窗口后全部停止，无 QThread 警告

## ConfigWindow row_last 崩溃 + snap7 "Job pending"
文件：plc_window.py、plc_manager.py

1. `AttributeError: 'ConfigWindow' object has no attribute 'row_last'`
   根因：`row_last`/`col_last` 原来在 `plc_mgr.read_data(22,2,1)` 之后才赋值，
   PLC 断线时 data 为 None → 构造函数中途 return → 后续按钮信号连接、属性
   全都跳过，点击仓位即崩。
   修复：① `row_last`/`col_last` 提到任何 PLC 读取之前赋 0；② 读不到按 (0,0)
   处理，不再 return；③ `_on_toolButton_hostX_rackX_click` 加 row/col 范围
   校验；④ 高亮取消走新增的 `_set_rack_status_color_safe()`。
   另确认：场景图元 `料架1..10` × `仓位1..8` 与 rack_status 的 10×8 完全一致，
   `on_slot_clicked` 的 rack_no-1 / slot_no-1 换算正确。

2. `b'CLI : Job pending'`
   根因：snap7 一条 TCP 连接上不能并发提交作业。轮询线程（QThread）与 UI 线程
   同时 db_read/db_write 就会撞车，随机一次失败被误判成断线 → 触发重连风暴。
   修复：plc_manager 新增 `_IOLock`（带优先级的互斥锁，与只保护状态机的
   `self.lock` 分开），read_data/write_data 加 `priority` 参数。
   UI 侧 39 处调用统一传 `priority=True`，轮询默认低优先级且遇高优先级等待时让路。
   实测（单次 IO 50ms + 持续轮询）：普通 Lock 最大 1009ms/平均 399ms，
   _IOLock 最大 101ms/平均 76ms；8 线程并发压测并发冲突 0 次。
   注意：Lambda 里的 write_data 正则替换容易搞错括号位置，改这类代码优先逐行 Edit。
