## PopPick：双击背景收起/展开左侧页面

需求：双击背景收拢左边卡片，再双击展开，带动画。

### 实现
- `PageDeck` 把「交换」的动画内核抽成 `_start_motion(motions, kind, duration_ms, arc_len)`：
  交换（2 张 + 弧线 + 收尾换 Z）和收拢/展开（N 张 + 直线 + 收尾只落位）共用一套
  插值、快速渲染开关、busy 信号。`_from`/`_to` 字段随之下线，收尾统一按
  `_Motion.end` 落位（等价且更不易漂）。
- 新增 `fold()/unfold(immediate=)/toggle_fold()/refold()/is_folded()` + 信号 `fold_changed(bool)`。
  收拢形态：角度全部归 0、中心重合、整摞贴到视口左边缘只露 `FOLD_PEEK_PX=36px` 当把手。
  `_fold_saved` 记的是**收拢前那一刻**的位姿（不是设计初始值）——交换过之后谁在哪儿已经变了。
- 窗口侧：`MouseButtonDblClick` 判定；折叠状态下任何位置双击都展开（否则用户会去双击
  那条把手，按"必须点空白"判会完全没反应）。

### 踩的坑
- **坐标跨了两套**：`FOLD_PEEK_PX` 是窗口像素，`sceneToView` 给的是视图坐标，差一次
  `×scale + offset`（`pos_view_toWindow`）。第一版直接拿视图坐标比 26px，整摞被推到窗口
  左边之外——测试全绿（断言也用了同一套错误换算，自洽）但截图里卡片"点一下就没了"。
  **教训：涉及"贴屏幕边缘"的量必须落到 window 像素，回归断言要单独用 window 坐标复核。**
- 离屏 `win.grab()` 抓不到变化，是因为双击点 (0.5, 0.93)*视口 实际命中了卡片（缩放后
  卡片占了大半屏），折叠根本没触发。选空白点要扫候选而不是拍脑袋。

### 后续调整：最前面那张不动（用户反馈）
最初把 5 张全收进视口左边缘只露 36px 把手，用户要求"最前面这张位置不用动"。
改成：**stack[0]（Z 最高）原地不动，其余 4 张旋转角与中心都对齐到它**，叠成整齐一摞。
连带简化：
- `_fold_saved` 只记 stack[1:]（最前那张本来就没挪，不需要还原）；
- `_fold_targets` / `_flat_view_size` / `refold()` 全部删除——落点就是场景里那个锚点，
  和缩放无关，滚轮缩放不再需要 `QTimer.singleShot(0, refold)` 补救；
- `FOLD_PEEK_PX` 常量删除。
回归从"贴边 36px / zoom 后仍贴边"改判为"**最前面那张位姿一字不差**"+"缩放后仍重合"。

### 连动
- 折叠状态下禁止 `swap_with_slot`（左侧卡已不在"页签"位置）。
- 点左侧只提示不交换；`_fit_view`/`_maximize_view` 前先 `unfold(immediate=True)`
  （收进屏幕外的卡会把适应窗口的包围盒拉爆）。
- 滚轮缩放后 `QTimer.singleShot(0, deck.refold)` 重算落点（场景在 eventFilter 返回后
  才处理缩放）；拖动平移不用管。
- 收拢动作同时解除 `_maximized` 锁定。

### 验证
`tools/verify_pop_pick_swap.py` 51 → **70 项全绿**（新增 19 项：中间帧、角度归零、
中心重合、贴边 36px、当前页不动、禁止交换、点左侧提示、缩放后 refold、展开回到收拢前、
把手双击、取景连动、收拢动画期间的快速渲染开关）。其余四套回归不变：
embedded_widget 通过、unified_entry 18/18、run_selection 14/14、group_visibility 16/16。

## 最大视图下锁定页放开交互（按钮能点）

需求：最大窗口时左侧最上层被锁定（不能交换），但**页内按钮必须能点**。

### 做法
- `pop_pick_entry.py` 新增 `_set_maximized()` / `_sync_card_readonly()` / `_locked_card()`：
  常规视图全部卡片 `set_widget_readonly(True)`（鼠标穿透 → 点击落到场景 = 一次交换）；
  最大视图下**只把被锁定那张**设成 `readonly=False`，其余保持穿透。
- 所有 `self._maximized = X` 的赋值点统一改走 `_set_maximized()`（reset / fit / maximize /
  fold / Wheel 五处），避免漏同步。
- `_on_swap_finished` 里补一次 `_sync_card_readonly()`：交换会互换 Z，"堆叠最上层"换人，
  放开的卡要跟着走。
- `embedded_widget_layer._apply_interactive` 退回只读时补 `widget.clearFocus()`
  （否则鼠标已穿透、键盘还在往那一页里打字）。
- 状态栏文案改成"已锁定（页内可操作）"。

### 顺带修掉的真 bug：快照丢背景
跑回归时"快速渲染前后不失真"从 1.45% 掉到 **23.91%**。根因不是定位/缩放，而是
`widget.render(painter, ..., QWidget.DrawChildren)` **少了 `DrawWindowBackground`**：
卡片根控件是 `QTextEdit`（样式表自带 background-color + `WA_StyledBackground`）时没问题；
用户把槽位卡换成 `ConfigWindow`（QMainWindow 子类，背景靠窗口背景填充）后，只画子控件
烘出来是**透明底**，快照期间整张卡透出场景的淡绿底色。改成
`DrawWindowBackground | DrawChildren`（`QWidget::grab()` 内部就是这一组）后回到 1.43%。
**教训：烘控件快照要照抄 `grab()` 的 renderFlags，不能省 DrawWindowBackground。**

### 验证
`tools/verify_pop_pick_swap.py` 70 → **76 项全绿**：锁定页 readonly=False、其余仍只读、
承载视图不再透明、页面里塞一个 QPushButton 真点一下命中 1 次且不触发交换、退出最大视图
后全卡恢复只读且视图恢复穿透。其余四套保持：embedded_widget 通过、unified_entry 18/18、
run_selection 14/14、group_visibility 16/16。

### 追加：放开交互的改成"前端两页"（用户要求）
`_locked_card()` 语义改了：不再指"被锁的那一张"，而是返回**最大视图下放开交互的
两页** `(右侧当前页, 左侧堆叠最上层)`，非最大视图返回 `()`。锁定（不允许点走）
另立 `_unswappable_card()` = `stack_cards()[0]`，`_is_locked_card()` 只认它——
右侧是槽位，点了本来也不交换，不需要拦。
`_sync_card_readonly()` 用身份比较（`any(card is other ...)`）判断是否可交互。
回归 76 → 79 项：新增"右侧当前页也恢复可交互""右侧页内按钮收到点击"。

## 设计态 widget 图元只能点边框选中（已修）

现象：设计模式下 click 控件图元只有贴着边的一条带能选中，点中间毫无反应。

根因：命中不看 `shape()`，而是 `single_select_handle()` 遍历 `get_hover()`，
hover 由各图元自己的 `check_hover(mouse_pos)` 算。`rect_element.check_hover`
对**无填充**矩形只认"边框 ±10px"那条带（中间挖空，防止空心框挡住下面图元），
`widget_element` 直接继承了它 —— 控件是一块实心面板，中间就被挖掉了。

修法：`widget_element.check_hover` 覆写，整块 `QRectF(_head_pos, _end_pos)` 都算命中
（局部坐标已按中心归一化，旋转由 `mapFromScene` 的逆变换消掉）；末尾再调
`base_element.check_hover(self, ...)` 补上成组悬停信号（放在 set_hover 之后，
本帧就能通知出去）。父类 rect_element 的行为不动。

坑：`completed()` 之后 `is_moving()` 仍为 True（要等 paint 里 `_reset_moving_flag()`），
测试里直接调 `check_hover` 必须先手动清一次，否则永远返回 False。

回归：`tools/verify_embedded_widget.py` 新增 6 项（中心命中/靠边命中/外部不命中/
纵向外部不命中/父类规则对照中心不命中/点中间能被单选选中），全套仍"全部通过"。

## 框选时属性面板不跟随（已修）

现象：Ctrl + 拖拽框选后画布上有蓝框、图元也确实被选中，但属性面板停在框选前那个对象上。

### 两个真 bug（都在 `myGraphicsScene.FrameSelect`）
1. **矩形没归一化**：`QRectF(end_pos, start_pos)` 不做归一化，从右下往左上拖时宽高是负数，
   `contains()` 全部返回 False —— 四个拖拽方向里只有"左上→右下"能用，另外三个方向
   看着有虚线框却一个都选不中。`receive_end_pos` / `finish` 里都补 `.normalized()`。
   顺带：`select_rect`（屏幕坐标那份）也一起归一化，虚线框才不会翻转。
2. **框选不发 `selectionChanged`**：框选只给各图元 `set_selected(True)`，不走
   `single_select_handle`，没人发信号。属性面板、状态栏、删除/排列动作的可用性全挂在这个
   信号上，漏发就等于"框选只在画布上留了个蓝框"。新增 `myGraphicsScene.frame_selection_finished()`
   统一通知，`current_selected` **故意不动**（`mousePressEvent` 里 Ctrl 起框要求
   `current_selected is self`，改了就得先点空白才能再框）。

### 面板侧改造
- `selected_top_level_items()`（scene 上新增）：按 `selected` 标志收集顶层图元、按 z 排序。
  **选中集合才是真相**，`current_selected` 只是"最近点到的那一个"。
- `design_window._panel_target()`：1 个 → 该图元；多个 → 传列表；0 个 → 退回
  `current_selected`（组内成员走这条）或场景。若 `current_selected` 已不再选中（Esc 清空、
  删除）则回退场景——否则面板会停在一个失效的选中状态上。
- `NavigationContentWidget` 支持 list/tuple：`_show_multi_selection_pages()` 出「选择概要」
  （数量/类型统计/包围盒/Z 范围）+「图元清单」两页，头部字牌"多"。多选不做字段编辑：
  逐个图元的编辑器都绑定在单个对象上，硬套会让人以为改动批量生效。
- `_update_selection_actions` 现在按选中数量开关排列动作（≥2 可用）。原来这几个动作常开，
  注释里写着"rubber-band 不发信号，所以不敢关"——这个前提没了。
- `_update_status` 追加"已选 N 个"；`myGraphicsScene.clearSelection` 补发 `selectionChanged`；
  `_restore_group`（属性面板里恢复隐藏组）补 `set_selected(True)`，否则按选中集合判断时
  会被当成"没选中任何顶层图元"。

### 坑
- `base_element` 的 z 取值接口是 `zValue()`，**没有** `get_zValue()`（`group_element` 会直接
  AttributeError）。写排序/范围时用 `zValue()`。
- 测试里用"包围盒正好等于拖拽框"构造命中，浮点边界会让 `contains()` 时真时假；
  断言用的框要 `adjusted(-60,-60,60,60)` 留边距，否则看起来像"方向失效"。
- 用替身对象测 `_on_scene_selection_changed` 时替身必须继承 `QObject`：方法里用
  `self.sender()` 判断信号是不是当前页场景发的，普通对象没有 `sender()`，异常被 Qt 吞掉，
  表现为"信号发了但面板没刷新"。

### 验证
新增 `tools/verify_box_select.py`（**31 项全绿**）：四方向拖拽、零命中、每组一次信号、
`current_selected` 不变、组内成员不被单独框选、单选/多选/空选的面板目标与分页、
清空选择回退、状态栏数量、排列/删除动作可用性、以及"信号 → 面板实际刷新"的端到端链路。
其余：property_panel 全通过、embedded_widget 全通过、unified_entry 18/18、run_selection 14/14、
group_visibility 16/16、group_tab_cycle 无失败、widget_clone_geometry 13/13、pop_pick_swap 79/79。

### 顺手修的两个测试脆弱点（非产品 bug）
- `verify_pop_pick_swap._hit_point` 采样网格太稀（只取 0.1~0.5/0.2~0.8），卡片包围盒被
  伸出卡面的子图元撑大后找不到命中点 → 改 19×19 网格。
- 同一脚本把堆叠顺序写死成 `["Page1","Page3","控件_11","Page4","Page5"]`，页面文件一改就红 →
  改成不变量断言（按 z 降序、且等于"除槽位卡外的全部卡片"），底层卡也改成 `stack[-1]`。

## 收起状态的交互口径调整（双击只认空白 + 两页可交互）

### 需求
1. 收起状态下双击左侧封面**不应**展开，只有双击空白背景才行；
2. 收起状态下剩下可见的那两页不可再交换；
3. 那两页里的控件必须可交互。

### 做法
- `pop_pick_entry.py`：双击分支去掉 `deck.is_folded() or` 的豁免，只判 `not on_card`。
  收起时那两页已放开交互，事件本来就落在页内控件上，这条判断是兜底。
- `_locked_card()` 改名 `_interactive_cards()`：`_maximized or deck.is_folded()` 时返回
  `(右侧当前页, 左侧堆叠最上层)`，否则空元组。`_sync_card_readonly()` 据此放开只读。
- `_unswappable_card()` 同样纳入 `is_folded()`——收起时左侧封面就是"用户正看的封面"，
  一点就跑掉等于换了画面。`_handle_click` 里 `self._maximized and ...` 的额外判断去掉，
  交给 `_is_locked_card()` 自己判状态。
- `_install_deck` 里把 `deck.fold_changed → _on_fold_changed → _sync_card_readonly`
  接上：`reset()`、`_unfold_if_folded()`、动画被打断等路径都会改变折叠状态，
  逐处补调用必漏。信号在 fold/unfold **动画结束时**发（`_on_finished`）与打断时发
  （`_cancel_animation`），所以收起动作刚发起时还会多走一次 `_set_maximized(False)`
  的同步，两者幂等。

### 验证
`verify_pop_pick_swap.py` 79 → **91 项全绿**。新增：收起后封面/当前页 readonly=False、
其余仍只读、两者承载视图都不再穿透、两边各塞一个 QPushButton 真点命中 1 次且不交换、
展开后恢复全只读、折叠时双击左侧封面不展开、双击右侧当前页不展开、双击空白仍能展开。
其余套件保持：embedded_widget 全部通过、unified_entry 18/18、box_select 全部通过、
property_panel 全部通过、run_selection 14/14、group_visibility 16/16。

### 注意
Page1（收起后左侧封面用的那张）的控件本身在离屏平台下几乎全白（`view.grab()` 非白像素
只有边框那点），展开时也一样——这是该页控件自身的内容问题，与本次交互改动无关。

## 最大视图下的收起/展开：锁定要跨过折叠状态

需求：在最大窗口状态下双击空白背景收起、再双击展开后，**仍算最大视图**——最前页继续
不可交换，但页内控件可交互。

改动：`_toggle_fold()` 的 fold 分支不再 `_set_maximized(False)`。理由：最大视图是**取景**
状态，收起/展开只是把左边那摞挪一挪，取景没变；锁定语义应当跟着取景走，而不是跟着
堆叠形状走。展开后 `_interactive_cards()` / `_unswappable_card()` 因为 `_maximized` 仍为真
会自动给出正确结果，不用另写分支。退出锁定只认「适应窗口」/滚轮缩放/「最大窗口」重算。

状态栏文案分两套：最大视图下收起提示"仍在最大视图：最前页不可交换"，常规视图下提示
"两页均可直接操作"。

### 验证
`verify_pop_pick_swap.py` 91 → **107 项全绿**。新增：最大视图下双击空白能收起、收起后
仍是最大视图、最前页仍被锁定且仍可交互；展开后仍停在最大视图、最前页仍不可交换且仍可
交互、当前页仍可交互；最前页内按钮真点击命中 1 次且不交换；场景级点击也不交换；
「适应窗口」才解除锁定并恢复全卡只读。

### 两个测试侧修正
- `_blank_point()` 原先是 4 个固定候选点，最大视图下卡片占满屏幕时全部命中卡片，
  折叠根本没触发（断言却在"未折叠"状态上继续跑，看起来像别的断言通过）。
  改成 25×25 网格扫描 + 取离中心最远的空白点。
- 最大视图下空白只剩四角（实测 1280×820 时最远空白点是 (1242, 23)），提示语里别再写
  "双击空白背景恢复交换"——双击只会收起/展开，解除锁定得靠「适应窗口」。

## 图片图元：页面只存文件名

需求：`myPropertyForElement.ImagePropertyItem.select_image` 应当返回文件名（如 `bg.png`）。

原实现存的是 `os.path.relpath(file_path, Designer/Core)`，而 `image_element.set_image_path`
把它交给 `res_mng.get_img_path()`（拼 `<res>/myDesigner/img/<x>`）——两段都带相对前缀，
实际拼出 `res/res/myDesigner/img/...`，路径是坏的（`page_9.json` 里那条
`..\..\res\myDesigner\img\9#Q1P拣选Q3P拣选.png` 就是这个 Bug 的产物）。

改法：
- `select_image() -> str`：返回最终文件名，取消选择返回 `""`；写回图元后同步刷新只读
  输入框（`self._source_edit`，页重建时重新赋值）。
- 新增 `_import_image()`：选中的图片先 `shutil.copyfile` 到 `res/myDesigner/img`，已在
  目录里（绝对路径相同或内容相同）就沿用原名；**同名不同内容不覆盖**，改叫 `bg_1.png`
  ——资源目录是多图元共用的，静默覆盖会连坐。
- `_ResourceManager.get_img_dir()`：新增，返回 `<res>/myDesigner/img`（`get_img_path("")`
  也能凑出来，但抽个方法更直白）。
- `image_element.set_image_path()` 兜底做 `basename`：老 JSON 里的相对路径/`res\x.png`
  这类脏数据加载后自动收敛成文件名，`image_path()` 反读就是干净的 `bg.png`。

回归（临时脚本，跑完已删）：返回名、写回名、文件已复制、重复选不产生 `_1` 副本、

`verify_property_panel.py` 仍全部通过。

### 追加：图片过滤器放开
`QFileDialog.getOpenFileName` 的过滤器改成
`图片文件 (*.png *.jpg *.jpeg);;PNG 图片 (*.png);;JPEG 图片 (*.jpg *.jpeg)`，提示文案同步改成

## PopPick：窗口尺寸变化后重算最大视图取景

现象：最大视图的缩放/平移是按**当时窗口尺寸**反算的，窗口一变（拉大/最大化）
那两页就缩在中间或溢出边界——`myQuadTreeScene.resizeEvent` 只重排嵌入式控件
几何，不动 offset/scale。

口径（用户确认）：**只在 `_maximized` 时重算**，普通视图（扇形全貌）一律不动；
连续 resize 用一个 80ms 单次定时器合并，拖动过程中不重算。

实现（`pop_pick_entry.py`）：
- `MAXIMIZE_REFIT_MS = 80`；`resizeEvent` → `_schedule_maximize_refit()` → `_refit_maximized()`。
- `_maximize_view(*, announce=True, unfold=True)` 加了两个开关：
  - `announce=False`：重算不往状态栏再播一条"已放大到最前面两页"（否则拖一次刷一条）。
  - `unfold=False`：**最大视图 + 已收起可以同时成立**，重算取景不该顺手把卡摊开。
    工具栏按钮走默认 True（重新取景本就意味着回到全貌）。
- 定时器在 `closeEvent` 里 stop。

顺带修了回归脚本一处**早已失效**的断言：`Z 值落地为连续整数` 写死 `[1..6]`，
页面被设计器重存后底数变成 14~19（Z 计数不回退），改成"连续且互不相同"。

回归：`verify_pop_pick_swap.py` 107 → **123 项全绿**（新增 16 项：普通视图改尺寸
不进最大视图/不锁卡/不改缩放；最大视图下定时器先挂起、变小后缩放按新尺寸重算、
仍最大视图、不重复播报、两页仍完整在窗口内且填充≥90%、仍锁定；收起态改尺寸不
展开且状态保持）。`verify_embedded_widget.py`、`verify_unified_entry.py` 18/18 仍通过。

## PopPick 关窗后「工具页没恢复」：幽灵控件

  `_release_widget()`（内部 → dispose → clear_widget）。

排查手法备忘：
- `app.topLevelWidgets()` 里 `isVisible() and parent() is None` 的 QTextEdit/QPushButton 就是幽灵；

## PopPick 关窗后「工具页不出现」追到底层：PLC 线程 + isVisible 陷阱

用户贴出满屏 `TCP : Unreachable peer` / `尝试重连...(192.168.1.1, 第N次)`，问是否与 PLC 有关。
**结论：PLC 不是直接原因（心跳/重连都是后台 daemon 线程，不阻塞 UI），但它牵出两个真 bug，
外加一个我自己写错的死代码。**

### 1. 关窗后 PLC 线程从不停（真 bug）
`Page0/1/3_Model` 各建一个 `PLCManager` + `DataBroker`，宿主关了没人停：
- `PLCManager` 心跳线程（`threading.Thread`，daemon）+ 重连线程；
- `DataBroker` 的 `PollingThread`（**QThread**）。

后果：面板关了还一直刷"尝试重连"；QThread 在对象回收时仍在跑，Qt 会直接终止进程。
修法：
- `PLCManager.shutdown()`：**只置标志、不 join、不 disconnect**（重连线程可能正阻塞在
  `client.connect()`，另一线程并发 `destroy()` 会让 snap7 崩）。socket 交给线程自己在
  退出那一轮 `disconnect()`。
- 新增 `_stop_event = threading.Event()`：退避原来是 `threading.Event().wait(delay)`，
  `shutdown` 叫不醒，得把 15 秒睡完才退出；改成 `self._stop_event.wait(...)`，`shutdown` 里 `set()`。
- `rack_global_parameters_model._PlcBackendMixin.shutdown()`：先 `stop_data_polling`，
  再 `mgr.shutdown()`；三个 Model 都继承它。`__init__` 里先把 `_plc_mgr/_data_broker`
  置 None（场景里找不到图元时提前 return，否则关窗 AttributeError）。
- `PopPickWindow` 用 `self._page_models` 持引用（QObject 子对象只挂 parent 拿不到 Python 句柄），
  `closeEvent` 里逐个 `shutdown()`。

### 2. `stop_data_polling` 把关窗卡住 544ms（自己踩的）
`wait_ms` 默认 5000，`PollingThread.OFFLINE_INTERVAL_MS` 是 500 —— 线程在 msleep 里
才看 `isInterruptionRequested`，所以关窗干等了 500ms。实测 `close()` 从 28ms 涨到 544ms，
而 `_back_to_launcher` 是 `QTimer.singleShot(0)` 排的，被这 544ms 一起推后 →
**屏幕上空白半秒**，观感就是"没恢复"。改：`OFFLINE_INTERVAL_MS=100` + `wait_ms=300`，
关窗回到 99~121ms。

### 3. `isVisible()` 对最小化窗口返回 True（我的死代码）
`_back_to_launcher` 原来：
```python
if self.isVisible():
    self.raise_(); self.activateWindow(); return
```
最小化的窗口 `isVisible()` 仍是 True → 直接 return → 下面的 `setWindowState(...&~Minimized)`
`showNormal()` `_restore_on_screen()` `_force_foreground()` **全是死代码**。
改成先算 `minimized` / `offscreen`，三者都 OK 才快退：
```python
minimized = self.isMinimized() or bool(self.windowState() & Qt.WindowMinimized)
offscreen = not self._is_on_screen()
if self.isVisible() and not minimized and not offscreen: raise_(); return
```
`_raise_launcher` 同理先 `showNormal()` 再抬。新增 `_is_on_screen()`（与任意屏幕
`availableGeometry()` 相交）。

### 4. 诊断落地：默认写日志文件
`APPS_LAUNCHER_TRACE` 改成默认开（`!= "0"`），并且**始终追加写**
`%TEMP%\apps_launcher_trace.log`（>256KB 自动重开），不再只打 stderr —— 这样用户跑一次，
我直接读文件。关窗后还起一个 500ms × 12 次的采样器（`_start_launcher_diag`），每行记录
visible/minimized/state/geom/active/screen/tops，用来区分"没 show / 被最小化 / 在屏外 /
被别的顶层窗口盖住"。

### 5. 顺手恢复 resize 守卫
`resizeEvent` 与 `_refit_maximized` 里被注释掉的 `if self._maximized:` 恢复，
`verify_pop_pick_swap.py` 回到 **124/124**；`verify_unified_entry.py` 21 → **26 项**
（新增最小化回落 3 项、屏外回落 2 项）。其余 embedded / clone 13/13 / box / property 全通过。

**记忆点**：`QWidget.isVisible()` 不排除最小化状态；判断"用户能看见"必须
`isVisible() and not isMinimized() and on_screen`。

## 关窗「界面卡死」真凶：原生 WM_CLOSE 段错误（至此收口）

现象：点 PopPick 标题栏 × 后**工具页出现了，但整个界面卡死**（点什么都没反应）。

### 定位过程（可复用）
1. 用户 trace 停在 `收到活动窗口 Close` → `回到选择页`，之后**连 500ms 的 diag 采样都没有**
   → 事件循环停转。但 `[pp-close] closeEvent 进入` 也没出现 → closeEvent 根本没进。
2. `main.py` 加 **faulthandler.enable(file=%TEMP%\apps_launcher_fault.log)**：
   拿到 `Windows fatal exception: access violation`，进程是**段错误退出（exit 139）**，
   不是"卡"——窗口留在屏幕上不重绘，看起来就是卡死。
3. 加**主线程看门狗**（`_MainThreadWatchdog` + 200ms QTimer 心跳，停 3 秒抓全部线程栈）。
4. 三组对照实验（探针脚本，已删）：
   - `--no-restore`（不回落）→ **仍崩 139**，与 `_back_to_launcher`/showNormal 无关
   - `--bare-close`（closeEvent 只 accept）→ **仍崩**，连"裸 closeEvent"都不打印
   - `--no-wm`（改用 `window.close()`）→ **exit 0 正常**

**结论：崩在 Qt 处理 Windows 原生 WM_CLOSE 的内部（在调用 Python closeEvent 之前），
与关闭清理、回落窗口都无关。** 程序内 `close()` 完全正常，点 × 就崩。

### 修复
`pop_pick_entry.py` 新增 `_DeferredNativeClose` mixin（`PopPickWindow` 第一个基类）：
```python
def nativeEvent(self, event_type, message):
    if _is_native_window_close(event_type, message):   # 读 MSG.message == 0x0010
        QTimer.singleShot(0, self.close)               # 延后一轮，走正常 close()
        return True, 0
    return super().nativeEvent(event_type, message)
```
`_is_native_window_close` 只认 `windows_generic_MSG` / `windows_dispatcher_MSG`，
非 win32 一律 False，跨平台安全。

验证：真实 WM_CLOSE（`PostMessage(hwnd, WM_CLOSE)`，等同点 ×）连跑 **3 次 exit=0**，
`closeEvent` 全程走完，`beat` 持续推进，launcher 可见。

### 顺带修掉的三个真 bug（都是崩溃的"另一条腿"，别再退回）
1. `snap7_plc_manager._close_client()`：原来**不持 `_io_lock`**，`client.destroy()`
   与轮询线程的 `db_read` 并发 → 访问已释放的 C 指针。现在整段持锁，并且
   **destroy 后同步 `self.connected = False`**（原来只清 client 不清标志）。
2. `snap7_data_broker.PollingThread.run()`：原来每轮都摸 `self.broker.data_ready`
   ——broker 的 C++ 对象随宿主窗口销毁后，这一下就是段错误。现在开头缓存局部
   `broker`，每轮 `shiboken6.isValid(broker)` 守卫，`_read_and_emit` 改成传 broker 参数。
3. `stop_data_polling(wait_ms)` 现在**返回 bool**；`_PlcBackendMixin.shutdown()` 里
   等不到线程退出就 `keep_alive_until_stopped(broker)`：`setParent(None)` 摘出销毁链、
   挂到模块级 `_ORPHANS` 保活，线程 `run()` 的 `finally` 里再移除。

### main.py 的改动（保留）
- `_back_to_launcher` 里**同步只做 `showNormal()`**，`raise_/activateWindow/SetForegroundWindow`
  全部移到 `QTimer.singleShot(0, _raise_launcher)`——不要在 Close 处理栈里抢前台。
- 快退分支（本就可见）同样只排 singleShot。
- `faulthandler.enable()` 常开写 `%TEMP%\apps_launcher_fault.log`；
  主线程看门狗停转 3 秒 dump 全部线程栈到 `%TEMP%\apps_launcher_trace.log`。

### 回归
`verify_pop_pick_swap.py` 124 → **126**（新增「原生 WM_CLOSE 被拦截」「拦截后窗口确实关掉」，
用 `wintypes.MSG()` + `nativeEvent(b"windows_generic_MSG", addressof(msg))` 构造）；
`verify_unified_entry` 26/26、embedded / box_select / property_panel / widget_clone_geometry 全通过。

**未做**：安全车、料架窗口没加同样的 WM_CLOSE 拦截。它们的关闭路径在回归里正常，
但「点 × 走原生消息」这条风险仍在——若哪天也报卡死，照抄 `_DeferredNativeClose` 即可。

## 新增 OPC UA 通信层（common/com/opcua）

**背景**：PopPick 要走 OPC UA 和 PLC 通信，需要一条与 `common/com/snap7` 平级的通道。

**落地**：
- `common/com/opcua/opcua_manager.py` —— `OpcUaManager(QObject)` +
  `OpcConfig`。对外只暴露**同步** `read` / `write`（手感对齐 snap7 的
  `read_data` / `write_data`），内部把 asyncio loop 放独立 daemon 线程，
  用 `run_coroutine_threadsafe().result(timeout)` 桥接。
- 信号：`connected_changed(bool)` / `state_message(str)` /
  `node_changed(str, object)` / `node_error(str, str)`。
- `subscribe({key: node_id})` 可在 `start()` 之前调用（先配置后连接是常态），
  连接时自动补上；连接期间追加走增量订阅。
- `key` 不在订阅清单里也能直接当 NodeId 字符串读（免订阅单点读）。
- `stop()` 语义对齐 snap7 broker：返回线程是否真退出，False 时调用方必须
  用 `keep_alive_until_stopped()` 摘出保活。

**关键：不要自己写重连**。asyncua 2.1 的 `Client(auto_reconnect=True)` 自带
watchdog 健康探测（默认 1s）、指数退避（1s→2×→max 30s）、**订阅自动重建**。
只有当「首次连接就失败」时它才不管——那条路要自己 `_bootstrap` 退避重试
（现场常态：先开软件、后给 PLC 上电）。

**踩的坑**：
- `group.add_variable(idx, "Lamp01", val)` 里 `"Lamp01"` 是 **bname**，
  NodeId 会被自动分配成 `ns=2;i=3`；要字符串 NodeId 必须显式
  `ua.NodeId("Lamp01", idx)`。查了半天 BadNodeIdUnknown 是这个原因。
- 命名空间索引**不能硬编码 2**，用 `register_namespace()` 的返回值。
- `stop()` 必须取消 `_tasks` 里的 `_state_watcher` / `_bootstrap` 并
  `gather(return_exceptions=True)`，否则退出时报
  "Task was destroyed but it is pending"。
- `stop()` 成功退出后要清 `_subscribed` / `_nodeid_key` / `_nodes` / `_vtypes`，
  否则二次 `start()` 会认为"已订阅过"，跳过 `_apply_subscription`，
  新连接一条推送都收不到（`_desired` 要保留，那是用户意图）。
- `is_connected()` 直接查 `client.state`，比信号早一步变；界面状态要接
  `connected_changed`，别在 UI 里轮询 `is_connected()` 判断显示。
- `connected_changed` 的 False 用 `client.connection_lost_callback` 立即发，
  True 靠 200ms 的 `_state_watcher`（asyncua 没有"重连成功"回调）。
- 订阅建立时服务端会**先推一次当前值**，UI 不用额外读初值。

**验证**：`tools/verify_opcua.py` **45/45**（含断线→自动重连→订阅重建全链路）。
反向验证做了两项：去掉 `stop()` 里的订阅记录清理 → 二次 start 收到 0 条；
去掉 `subscribe_data_change` 调用 → 8 条订阅断言全挂。

**配套**：`tools/opcua_mock_server.py`（进程内 asyncua 服务器，String NodeId，
7 个节点含自增心跳）、`tools/opcua_demo.py`（界面 demo，可「停服务器」演示重连）。

**注意**：asyncua 带 cryptography，打包体积约 +38 MB；`hiddenimports` 需要
`collect_submodules('asyncua')`。没上 OPC UA 的 exe 别急着加。

### 补充：`tools/opcua_browse.py` 节点扫描器

### 补充 3：扫描"深度不够"的真因是命名空间剪枝，不是 --depth

**现象**：用户扫真实 PLC（`opc.tcp://192.168.1.100:4840`）只得到 3 个节点，
问"读取的节点深度是不是太少了"。根目录留下他导出的 `opcua_nodes.json`
（`ns=3;s="HMI_runTime"."second_totally"` 这类 S7 引号格式）。

**真因**：不是深度。原 `scan()` 里有两处按命名空间剪枝：

```python
if namespace is not None:
    if ns != namespace: continue      # --ns 3 时 Objects 的子全是 ns=0 → 0 结果
elif ns == 0 and path:
    continue                          # 第一层之后所有 ns=0 容器被剪
```

真实 PLC 的地址空间是**混合命名空间**的：S7-1500 是
`Objects(ns=0) -> DeviceSet(ns=0) -> S7-1500(ns=0/1) -> DataBlocksGlobal(ns=1)
-> "DB_Rack"(ns=3) -> 变量(ns=3)`，中间容器全在 ns=0。剪枝在第 1~2 层就断了，
`--depth 8` 形同虚设。实测：修前变量 0 个 / 目录 4 个；修后 13 个 / 16 个。

**修法**（原则：过滤只作用于输出，不参与遍历）：
- 容器**无条件递归**，只有 `STANDARD_SUBTREES`（ns=0 的 Server / TypeHierarchy /
  DataTypes / EventTypes / VariableTypes / ObjectTypes / ReferenceTypes / Views /
  ServerInterfaces）才剪。名单和 `is_standard_subtree()` 放
  `common/com/opcua/opcua_manager.py`，CLI + GUI 共用。
- `--ns` 只过滤**收变量**那一步；不指定时也排除 ns=0 的变量（方法参数
  InputArguments/OutputArguments、ServerStatus 这些噪音，之前被整片隐藏所以没露）。
- `--depth` 默认从 8 改成 **0 = 不限**。地址空间是有限有向图，有 `seen` 去重和
  `--max-nodes` 兜底，不需要人为层数上限。
- 截断提示拆成 `truncated_by_depth` / `max_nodes` 两种，说清是哪一个。
- 新增 `--start <NodeId>`，可从任意容器起扫（现场知道 DB 名时不用从 Objects 爬）。

**GUI 同一个病**：`_browse()` 里的 `namespace != 0` 把 DeviceSet 这类中间容器
也隐藏了，树在第 1 层就断，看起来"深不下去"。改成只隐藏 `is_standard_subtree`；
复选框文案改「隐藏内建类型子树」。反向验证：改回 `!= 0` 后根节点直接变空。

**验证**：新增 `tools/verify_opcua_scan.py` **29/29**（自建混合命名空间 12 层深树，
覆盖不限深度、ns 只过滤输出、depth 限深、内建剪枝、--start、订阅映射）。
反向验证：把命名空间剪枝加回去 → 7 项失败，核心断言「13 个变量」变成 0。
`verify_opcua.py` 仍 62/62。

（`ns=3;s="AGV-Rack"."Heartbeat"` → identifier 含引号和点，回转一致），
用户导出的映射表可直接 `subscribe()`。

## OPC UA 断线日志刷屏 / 断线中 stop 留 pending 任务（2026-11-05 傍晚）

**现象**：PLC 掉电后控制台每秒刷一段 `Publish iteration crashed; retrying in 1s`
+ 整段 traceback，指向 `ua_session._publish_loop -> publish -> _send_request ->
ConnectionError(Connection is closed)`。程序没崩，链路仍在自动重连。

**根因**：asyncua 2.1 在 supervisor 进入 RECONNECTING 后不暂停 publish 循环，
每次请求必然撞 `ConnectionError`，而它用 `logger.exception` 记这种预期内的失败。
没人配 logging 时由 `logging.lastResort` 打到 stderr（所以输出没有时间戳/级别）。

**修法**：`opcua_manager.install_quiet_reconnect()`（构造函数里调，幂等）给
`asyncua.client.ua_session(.UaSession)` / `asyncua.client.client` /
`asyncua.client.ua_client.UaClient` 挂 logger 级 filter，只丢「两条固定文案 +
异常是 `ConnectionError`」；ServiceFault、结构体解析失败、非 ConnectionError 全放行。
`OPCUA_LOG_NOISE=1` 可关。

**坑**：publish 循环用的是实例 logger `asyncua.client.ua_session.UaSession`（在
`UaSession.__init__` 里 getLogger），只挂模块 logger 拦不住；先
`logging.getLogger(名字)` 把 logger 建出来挂 filter，之后 `__init__` 取到同一个。

**第二个坑**：断线途中 `stop()` 会留下 `Task was destroyed but it is pending!`
（`UaSession._publish_loop`）。`UaSession.close_session()` 在「protocol 已为 None」
的分支里提前 return，跳过了 cancel publish 任务那一步。修法：`_shutdown_async`
里先 `_cancel_publish_loop(client)`（读 `client.uaclient._publish_task`、cancel +
`gather(return_exceptions=True)`）再 `client.disconnect()`。

**回归**：`verify_opcua` 62 → **74**。新增：过滤器三向单测（吞 ConnectionError /
放过 RuntimeError / 放过非白名单消息）、断线 3 秒内 0 条 publish 崩溃日志、
重连退避 warning 仍在、断线途中 stop 后 `publish_task.done()`。
反向验证：去掉 `install_quiet_reconnect()` → 漏出 4 条 + 2 项失败；
去掉 `_cancel_publish_loop` → 该断言失败且真的打 `Task was destroyed`。

## 真机连 PLC：`Reconnect attempt failed: TimeoutError()`（2026-11-05 晚）

**现场日志**：
```
Requested session timeout to be 3600000ms, got 30000ms instead
Reconnect attempt failed: TimeoutError(); retrying in 1.0s
```

**根因（读 asyncua 2.1 源码确认）**：
- `Client(timeout=...)` 是**每个请求**的超时，也用于 `send_hello` /
  `open_secure_channel` / `connect_socket` 的 `wait_for`（`ua_client.py`
  L303/L315/L567）。旧默认 4s，重连握手慢一点就 `TimeoutError()`，
  `_reconnect_with_backoff` 原样打出这条日志然后无限退避。
- `watchdog_intervall` **同时是健康探测的周期和超时**：
  `probe_timeout = min(revised_session_timeout/2, watchdog_intervall)`
  （`client.py` L949）。服务器把会话超时压到 30s 也没用，取 min 后仍等于
  watchdog。旧默认 1.0s = 每秒读一次 `Server_ServerStatus_State` 且只等 1 秒，
  真机偶发卡顿就被判掉线 → 白触发重连 → 重连又超时，正是这两行日志的链条。
- `Requested session timeout ... got 30000ms` 是协商 warning（asyncua 那行还
  误打了 `secure_channel_timeout`，但 `self.session_timeout` 确实回写成 30000）；
  本身不是错误，只是让 probe 公式里的 30000/2=15s 显得更冤。

**复现实验**：慢 `server_state.read_value`（sleep 1.2s）下，
watchdog=0.3s → 3 秒内状态反复跳变 11 次（误判）；watchdog=3.0s → 0 次。
重连指向「只 accept 不回 Hello」的黑洞端口 + timeout=0.5s →

## 导出结构崩 `UnicodeEncodeError: surrogates not allowed`（2026-11-05 晚 5）

**现场**：GUI 右键「导出此节点结构…」在
`Path(path).write_text(...)` 抛
`'utf-8' codec can't encode characters ... surrogates not allowed`。
汇川 Inovance / .NET 系服务端的字符串值里带**孤立 UTF-16 代理项**
（`\udcxx`，中文或截断字符串常见）。Python `str` 能存、`json.dumps(
ensure_ascii=False)` 也不报错，只有严格 UTF-8 写盘时会炸。
`gvl_hmi_structure.json` 那个 0 字节空文件就是这次崩溃留下的（文件先被创建、
内容没写成）。

**修法**（新文件 `tools/opcua_json.py`）：
- `sanitize(obj)`：**序列化之前**递归把孤立代理替换成可见文本 `\udcxx`。
  **必须两步**——只在写盘时用 `backslashreplace` 的话，产出的 `\udcff` 会被
  JSON 当成 Unicode 转义，`json.load` 又还原成孤立代理；转成文本后文件里是
  `\\udcff`，读回来是 6 个可打印字符。
- `dump_json(path, payload, default=str)`：`json.dumps(sanitize(...),
  ensure_ascii=False)` → `write_bytes(text.encode('utf-8',
  errors='backslashreplace'))`。后者兜住 `default=str` 生成的字符串里残留的代理。
  中文原样保留（不用退化成 `ensure_ascii=True` 的 `\uXXXX`）。
- `clean_text()`：显示用，代理 → `\udcxx`；接进 GUI `_fmt()` 的所有返回分支，
  避免下一步在 QTreeWidgetItem / tooltip 上再崩。

**接入点**：GUI `_write_export()` / `_export_structure()`、CLI
`opcua_browse.py --json` 三处写盘全部改用 `dump_json`；两个文件里已无用的
`import json` 删掉。

**回归**：`verify_opcua_struct` 67 → **73/73**（新增 `[0]` 段：clean_text
保中文/去代理、_fmt 清洗、嵌套 payload 写盘后 json.load 成功且中文无损）；
`verify_opcua` 91/91、`verify_opcua_scan` 34/34；CLI `--json` 真实导出冒烟
（9 节点 / 23 个 struct_members）；编译与 GUI 离屏冒烟通过。
**反向验证**：把 `dump_json` 换回 `write_text(text, encoding='utf-8')` 且不
sanitize → exit=2，精确复现 `surrogates not allowed`。

## 打包：snap7.dll 没进包

现象：spec 里 `binaries=[]`、只收了 `res`，`dist/工具集/_internal` 里只有
`python_snap7-2.0.2.dist-info`，没有 `snap7/` 目录。

根因（三条叠加，缺一条都不会出事）：
1. python-snap7 2.0.2 的 dll 在 `site-packages/snap7/lib/snap7.dll`，由
   `snap7/common.py::load_library` 用 `ctypes.cdll.LoadLibrary()` **运行时**装载，

2. spec 的 `binaries=[]` 一个二进制都没声明，`datas` 只有 `res`。
3. `hook-snap7.py` 传的是 `runtime_hooks`，它跑在 exe 起来之后，只做
   `os.add_dll_directory` 改搜索路径，**不参与文件收集**。runtime hook 只能
   "找到"，不能"放进去"——这是最容易误判的点。

修复：spec 顶部 `from PyInstaller.utils.hooks import collect_dynamic_libs`，
`binaries=collect_dynamic_libs('snap7')`，实测返回
`[('...\\site-packages\\snap7\\lib\\snap7.dll', 'snap7\\lib')]`，正好对上
`_find_in_package()` 期望的 `<pkg>/lib/snap7.dll` 布局，连 runtime hook 都不用。

## 更正：surrogateescape 代理项必须可逆，不能转成文本（2026-11-05 晚 7）

**上一轮记的「代理项变 \\udcxx 字面量、信息不丢」是错的**，会坑到中文 NodeId。

查 `asyncua/ua/ua_binary.py` L104-120：`_String.pack/unpack` 都用
``errors="surrogateescape"``。国产 PLC（汇川）把 **GBK 字节**当 UTF-8 发，
客户端解码后每个非法字节变成 ``\udc80..\udcff``；**原样保留**这些代理字符，
编码时就能还原成服务端认得的原始字节。实测现场
`globalvars_structure.json` 里的 ``\udcb9\udca4...`` → GBK「工程描述」，
bytes = `b9a4b3ccc3e8caf6`。若变成中文文本或 ``\udcb9`` 可见字面量，
订阅就会 `BadNodeIdUnknown`。

**修正 `tools/opcua_json.py`**：
- `clean_text()`（**仅显示**）：把 `\udc80-\udcff` 连续段还原成原始字节，
  先试 UTF-8 再试 GBK，显示成中文；其余孤立代理变 `\ud800` 可见文本。
- `dump_json()`（**写盘**）：`json.dumps` 后把代理字符替换成 **JSON 转义序列**
  `\udcb9`（单反斜杠）——文件是合法 UTF-8，`json.load` 又还原成同一个代理字符，
  **NodeId 双向无损**。中文仍原样写入。
- `restore_escaped()`：把上一版误写成 ``\udcb9`` 字面文本的旧文件反向还原成
  代理字符，现场不用重导。

**`tools/opcua_from_json.py` 的 `load_tags()`**：
- 所有 node_id 过 `restore_escaped`；
- `variables` 段的 name 也先 `restore_escaped` 再 `clean_text`，中文名做 key
  （现场那个点现在是「工程描述」而不是一串 `udcb9_udca4_...`）；
- **同名变量加 `_2` 后缀而不是静默覆盖**——现场 `globalvars_structure.json`
  391 个点原来只加载出 195 个，现在 391 个全在；`opcua_nodes.json` 50 个
  （含 5 个冲突加后缀）。

**现场两份文件实测**：`opcua_nodes.json` = 50 点 / `192.168.1.88:4840`；
`globalvars_structure.json` = 391 点，含 1 个中文名点，NodeId 已可订阅。

**回归**：`verify_opcua_struct` 73 → **74/74**（改为验证 roundtrip 可逆、
GBK 字节一致、restore_escaped）；`verify_opcua_from_json` 21 → **25/25**
（+ 旧文件兼容 / 中文 key / 同名去重）；`verify_opcua` 91、`verify_opcua_scan` 34
全绿；编译与 GUI 离屏冒烟通过。
