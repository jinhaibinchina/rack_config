## struct 'f' vs 'd' 与 Modbus double64 改造

用户问 `struct.pack('d', v)` / `struct.pack('f', v)` 区别；结合其正在把
`fixture_config.MODBUS_REGISTER_MAP` 从 float32 改成 double64，顺带排查并修掉
`App_test_fixture/modbus_link.py` 三处会崩的遗留：

- `width()` 未识别 `double64` → 返回 1（应为 **4 字 / 8 字节**），导致批量读
  跨度算错、decode 只拿到 1 个字。
- `encode()` 的 `float32` 分支误写 `struct.pack('>d', ...)`（8 字节）再用
  `'>HH'` 解 4 字节 → `struct.error: unpack requires a buffer of 4 bytes`。
- `encode()` 的 `double64` 分支委托 `common.set_double()`：该函数用本机小端
  `struct.pack('d')` 配 `int.from_bytes(..., 'big')`，12.5 → `[0,0,0,0x2940]`，
  与 `decode()` 的 `>d` 不互逆，往返得 `5.2173e-320`。改为与 decode 严格对称的
  `struct.unpack('>HHHH', struct.pack('>d', v))` + word_order 处理。

**硬口径**：`'f'`=IEEE754 binary32=4 字节=2 个 Modbus 字、约 7 位有效数字；
`'d'`=binary64=8 字节=4 个字、约 15~16 位。改 double64 后 offset 步长必须按 4
递增，否则相邻点位重叠。

## 纠正：现场 PLC 是低字在前（用户实测）

用户给出 PLC 实测值：**12.5 = `[0, 0, 0, 0x4029]`**（4 个保持寄存器）。
我上午把 `encode/decode` 统一成网络序 `[0x4029, 0, 0, 0]`，虽自洽但与真机相反，
连上设备读数会是天文数字。三种口径区分：

| 4 个寄存器 | 含义 | 解出 |
|---|---|---|
| `[0x4029,0,0,0]` | 高字在前 + 字内大端（网络序） | 12.5 |
| `[0,0,0,0x4029]` | **低字在前 + 字内大端（现场 PLC）** | 整体反转后 12.5 |
| `[0,0,0,0x2940]` | 低字在前 + 字内小端（`common.set_double`） | 3.4e-315 |

修正：
- 新增 `_ordered_words()`：`little` = **整个字列表整体反序**，不是原实现的
  「两两交换」`(w1,w0,w3,w2)`；后者对 `[0,0,0,0x4029]` 只解出 5.3e-315。
  float32 只有 2 字时两者恰好等价，所以之前没暴露。反序是自逆运算，
  encode/decode 共用即保证严格互逆。
- `MODBUS_FLOAT_WORD_ORDER` 默认 `"big"` → **`"little"`**（映射表现已无 float32，
  11 个 double64 全部按 PLC 口径）。
- 门禁加 7 条 PLC 实测断言（`encode(12.5)==[0,0,0,0x4029]`、
  `decode([...])==12.5`、整体反序 vs 两两交换、big 仍输出网络序）。

## byte 类型（BOOL 按字节打包）写链路修正

用户把状态/命令点位改成 `type="byte"`（25 个）：现场一个 16 位寄存器放两个
BOOL，`byte=0` 用低字节 bit0（0x0001）、`byte=1` 用高字节 bit8（0x0100），
字里另一位必须保留。用户写的 `write()` 分支有 4 个问题：

1. `index_value = 1 << 8 if byte_index == 1 else 0` —— `byte=0` 时是 0，
   低字节写不进去。
2. `word += / -= index_value` —— 进位污染另一个字节、重复写不断累加、
   写 False 可能得负数、没有 `& 0xFFFF`。例：current=0x0100，byte=1，
   True → 0x0200（错）；current=0，False → -256。
3. `if "byte" not in spec` 放在读寄存器之后，非法配置白跑一次请求。
4. 两处调试 `print` 每次写都刷屏。

修法：模块级 `_byte_bit(spec)` 统一算掩码并对非法 `byte` 抛 `ValueError`；
`decode/encode/write` 三处共用；`write()` 结构化重写，`bit` 与 `byte` 合并成
同一套「先算掩码 → 读一字 → 位或/位与 → `& 0xFFFF`」幂等逻辑；调试输出改为
`DEBUG_WRITE = False` 开关。整个方法用 `build/_patch_byte_write.py` 按标记
替换（whitespace-only 行太多，Edit 不可靠），脚本已删。

**新增 `overlap_conflicts(map)`**：同一地址全是 `byte` 且 `byte` 值互异是合法
打包，不算冲突；其余重叠会被 `connect()` 警告。现场当前有 **6 个真重叠**：
100~104（状态 byte + 光电 byte + `fPositionNow`/`position_mm` 的 double64）、
112（`iState` double64 与 `sDriverErrorID` uint16）。未擅自改现场 offset。

**另**：配置里 `byte/2+100`、`offset/2+12` 是浮点除法，靠 `_reg()` 里的
`int()` 截断才正确，建议改 `//`；注释「11 个 BOOL 压在一个字里」也已过时。

**门禁同步**：状态位断言改用固定 `bit` spec（现场已换成 byte）；危险命令确认
断言按按钮 `confirm` 标志分支（现场 11 个 momentary 全设 False）。新增 7 条
byte 断言：写 True/False 保留另一字节、重复写幂等、decode 掩码一致、非法索引
报错、打包不算重叠、异类型重叠可检出。`verify_test_fixture` 及三个外围回归
0 失败，CLI 冒烟正常。
