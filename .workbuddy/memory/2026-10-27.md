### 两个关键坑（改这块代码前必读）
1. **隐藏仓位组会清掉子图元的状态标志**：`group.set_visibility(False)` 会递归把

## 修正：set_material 恢复用户原来的语义

用户指出 set_material 改错了。从会话记录里找回改之前的原文：

```python
def set_material(self, area, state) -> bool:
    """设置某个区域的料位状态（A/B/单库 → 空筒层 或 实料层）。"""
    name = normalize_area(area)
    self.set_part_visible(name, bool(state))
    return True
```

当时的 `MATERIAL_LAYERS` 是扁平元组 `("A库空筒", "A库实料", ...)`，
`normalize_area` 只做 `if key in MATERIAL_LAYERS`，所以 **area 传的是层名**，
state 是 bool（显示/隐藏这一层）。这是用户的设计，不要当成 bug 改掉。

现在两种写法都支持：
- 传层名（'A库空筒' / 'A库实料'）→ 原语义，`set_part_visible(name, bool(state))`
- 传区域（'A' / '单库'）→ state 按 MaterialState 解释，自动切换两层
  （`apply()` / 状态层走这条）
新增常量 `MATERIAL_LAYER_NAMES` 保存 6 个层名，供层名判定用。

教训：改别人写的函数前先 `git show HEAD:file` 对比，别把「另一种合法约定」当 bug。

## 15:55 text_element 内容变化时钉住左侧
- 需求：改 context 时文本框左侧位置不能动（原来 handle_context_change 保持 _center_pos 不动，长度变了左右对称撑开）。
- 关键事实：文本的长度方向是**局部 y**，不是局部 x。`is_use_for_agv_map=True`（本场景就是）
  时 sceneToView 是 view_x = -y*k，所以局部 +y 映射到视图左侧；普通模式局部 +y 映射到视图上方。
  paint 里把 w/h 换过来画，就是为了这个 90° 关系，别当成 bug 改。
- 实现：text_element.anchor_left_edge(old_h, new_h)：用 sceneToView 比两条候选边谁更靠左，
  得 sign=±1，再 _center_pos.y += sign*(half_old-half_new)。全在局部坐标算，旋转任意角度都成立。
  开关：类属性 keep_left_on_context_change（默认 True，设 False 回到老行为）。
- 四角仍由 _center_pos 派生，所以拖动 / to_dict→from_dict / update_boundingRect 都自洽，
  实测存盘往返画框完全一致（1e-6）。
- 回归测试：test/_smoke_text.py（左侧钉住、旋转 90° 只朝一侧长、往返一致、拖动自洽、开关生效）。

## 16:25 仓位几何反序（8-1）方案与干跑
- 用户要的是「图元的场景位置反序」：编号 1 挪到原 8 的位置，几何上下镜像，代号不动。
- 干跑验证（test/_dryrun_reverse_slots.py，不写文件）：按 scene y 排序后列表反转，逐个
  `group.change_position(get_scene_topLeft()+delta)`。料架2/5 全部对上，包围盒前后一致
  （-2606.423..3879.143），仓位1 y 3479.708 → -2206.988。
- 坑1：`setPos()` 在 is_in_group() 时直接 return（element.py:339），组内图元搬不动，必须用 change_position。
- 坑2：change_position 的入参是**目标场景左上角**（内部 mapFromScene 后当 topLeft），不是中心。
- 坑3：8 个目标位置必须先全部算完再统一写，1↔8 互换边读边改会互相污染。
- 用「按 y 排序 + 反转」而不是硬编码 y=9-n，间距不均/仓位不满 8 个时也成立。
- 反序会改变「PLC 位序 ↔ 物理位置」的对应：DB31/DB32 bit0 指向的格子变了，需与上位机确认。

## 16:41 确认：仓位几何反序不影响 PLC 映射
- 映射键是**名字里的仓位号**（SLOT_NAME_RE），坐标不参与；grep 过 rack_store_model /
  rack_stores_status_model / rack_status_panel_model / plc_window，没有任何按坐标排序或
  最近距离推断仓位的逻辑（唯一的 nearest 是灯色匹配）。
- 实测：反序后重新灌 bit0，数据仍进仓位1（A=实料1），只是仓位1 的 y 从 3479.71 变成 -2206.99；
  编号文本仍写进仓位1；点击信号发的还是同一个 slot_no。
- 结论：代码层映射零影响；变的只是「仓位号对应的物理格子」。要不要改取决于现场
  「1 号仓位」的编号方向（PLC 变量表 / 电气图 / AGV 取货顺序）。
